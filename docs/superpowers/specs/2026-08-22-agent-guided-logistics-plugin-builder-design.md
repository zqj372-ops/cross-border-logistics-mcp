# Agent 引导式物流插件构建设计

**日期：** 2026-08-22

**状态：** 已完成需求与设计确认，待书面规格复核

**范围：** 跨境物流领域的客户端接入与 Business Module 构建引导

## 1. 背景

仓库已有客户端接入说明、Module Runtime v0、Agent Standard Access、统一响应包络和业务模块开发规范，但缺少一条面向非技术使用者的完整入口。使用者通常只能描述一个模糊业务想法，不知道它应当通过客户端配置、现有工具组合、现有模块适配，还是新 Business Module 实现。

本设计建立一套供 Agent 读取和执行的构建协议。使用者通过自然语言描述想法，Agent 负责逐步诊断、核对现有能力、解释风险和数据权威边界，在用户确认后完成本地构建与验证。发布是独立阶段，必须再次授权。

本设计不把“插件”限定为单一技术对象，而是由 Agent 先分流为：

1. ChatGPT Work、Codex 或企业助手的 MCP 客户端接入；
2. 复用或组合仓库已有工具；
3. 配置或窄适配现有模块；
4. 新建跨境物流 Business Module；
5. 因权威源、契约或权限不足而暂不可构建。

## 2. 已确认事实与边界

- 当前 `main` 使用 Module Runtime v0，在进程启动时挂载静态可信模块。
- 当前运行时不支持远程安装任意插件，也不支持无需重启的生产 hot-plug。
- Module Contract v1、签名制品仓库、generation router 和完整隔离运行池是目标架构，不是当前已实现能力。
- Agent 必须从 `docs/agent/index.json` 解析适用 profile 和标准，不得把当前工作目录中的任意 Markdown 当成运行时权威。
- 报价、Zone、关税、订单、客户记录和文档等业务真相仍属于各自权威系统；MCP 是薄控制层。
- fixture、截图、聊天、公开搜索、代码存在和本地测试通过均不能证明生产可用。
- 统一业务状态仍只有 `success`、`needs_input`、`manual_review`、`blocked` 和 `unavailable`。

## 3. 目标与非目标

### 3.1 目标

- 让不理解 MCP、Schema、RBAC 或幂等的使用者也能从真实业务问题开始表达需求。
- 让 Agent 优先发现和复用现有能力，而不是默认生成新模块。
- 在写代码前形成用户确认的需求、权威源、风险、范围和验收标准。
- 为客户端接入、工具组合、模块候选和权威阻断提供确定的分流结果。
- 在确认后生成最小、封闭、可验证的本地产物。
- 清楚区分“已生成”“本地已验证”“fixture 已验证”“待适配验证”“发布阻断”和“已发布”。
- 将发布保持为独立授权和证据门禁。

### 3.2 非目标

- 不建立通用插件市场或任意领域的代码生成平台。
- 不实现远程任意代码下载、自动生产 hot-plug 或未经批准的静态注册修改。
- 不让模型生成或覆盖价格、Zone、税率、权限、容量、客户记录或业务状态。
- 不生成 `generic_write`、任意 URL、任意 SQL、任意脚本或万能编排入口。
- 不自动连接生产数据库、生产服务器或未批准的外部服务。
- 不在第一版自动执行发送、发布、订舱、报关、资金等 T3 动作。

## 4. 总体流程

Agent 按以下状态机推进：

```text
模糊想法
  -> 需求诊断
  -> 现有能力与权威边界核对
  -> 用户确认诊断卡
  -> 本地构建或配置
  -> 分层验证
  -> 已验证的发布候选
  -> 单独发布授权与门禁
```

在用户确认诊断卡之前，Agent 只能读取、分析、提问和提出方案，不能生成或修改实现代码。用户确认后，Agent可以在批准的仓库范围内自动构建。发布、外部连接、生产数据和真实写操作必须再次获得独立授权。

## 5. 入口与组成

第一版采用“机器可读流程 + 中文操作手册”，而不是单篇长教程或完整通用 CLI。

### 5.1 机器入口

计划在现有 Agent 标准体系中增加插件构建 profile、标准和 workflow。Agent 拉取仓库后先从 `docs/agent/index.json` 解析入口，再读取 allowlisted 文件。workflow 定义阶段、允许动作、问题类别、输出合同和门禁。

### 5.2 中文手册

中文手册面向人和 Agent，解释：

- 如何用业务语言描述想法；
- 两类“插件”的区别；
- Agent 为什么会逐题追问；
- 每种诊断结论意味着什么；
- 本地验证与生产发布的区别；
- 典型的客户端接入、现有工具复用、新模块和权威阻断案例。

### 5.3 受控模板

模板只承载已经批准的重复结构，例如诊断卡、客户端接入清单、模块最小骨架、RFC 和构建报告。模板不能绕过共享契约、工作流所有权或发布审批。

## 6. 需求诊断

Agent 每次只提出一个最能减少不确定性的问题，使用业务语言而不是一次性技术问卷。用户回答后，Agent 将信息转换成结构化需求；任何影响结果的未知规则都必须继续追问，不能自行补造。

### 6.1 诊断顺序

1. **真实目标：** 目前手工完成什么工作，最痛的步骤是什么。
2. **使用场景：** 谁使用、何时触发、输入材料、期望输出和是否需要人工复核。
3. **能力检查：** 当前工具、模块和客户端配置是否已经覆盖需求。
4. **数据权威：** 数据来自哪里、谁拥有最终业务真相、是否存在正式 API、版本和 readiness 证据。
5. **副作用：** 是否只计算、读取外部系统、写入内部记录，或产生不可轻易撤销的动作。
6. **验收标准：** 什么可观察结果才算本地构建成功，哪些内容明确不在范围内。

### 6.2 风险等级

- **T0：** 本地确定性纯计算。
- **T1：** 只读访问外部权威系统。
- **T2：** 产生内部业务写入。
- **T3：** 发送、发布、订舱、报关、资金或其他不可轻易撤销动作。

第一版可以自动构建 T0、T1，以及满足 preview→approval→commit→readback 条件的窄 T2。T3 只能形成设计、模拟验证和发布候选，不能自动执行真实动作。

### 6.3 诊断结论

诊断卡的结论只能是：

- `reuse_existing`
- `configure_client`
- `compose_existing`
- `new_module_candidate`
- `needs_more_information`
- `blocked_by_authority`
- `out_of_scope`

诊断卡至少记录：业务问题、使用者、触发条件、输入、输出、现有能力判断、权威源、副作用、风险等级、假设、缺失信息、明确非目标、验收标准和用户确认状态。

## 7. 分流后的自动构建

### 7.1 客户端接入

Agent 只生成或修改本地示例配置、环境变量清单和 staging 验证步骤。真实 token 只能通过受控 secret 或环境注入，不能写入仓库。除非完成当前环境中的工具目录、资源、身份和状态读回，否则不能声称客户端已接通。

### 7.2 复用或组合现有工具

Agent 生成调用方案，描述调用顺序、每一步输入输出、五种业务状态的处理方式、缺失信息如何回问以及人工复核责任。不得复制现有领域逻辑或新增万能编排工具。

### 7.3 新模块候选

经用户确认后，Agent 生成最小模块包：

- 已确认的诊断卡和需求记录；
- 当前可执行的 Module Runtime v0 manifest；
- Draft 2020-12 输入和输出 Schema，默认 `additionalProperties: false`；
- 单一职责的工具实现；
- 权威源适配端口；
- fake repository 或 fake HTTP 测试替身；
- 五种业务状态对应的必要示例；
- 单元、契约、权限、失败闭合和生命周期测试；
- 本地构建与验证说明；
- 发布候选清单和未验证项。

金额使用 decimal string 和 ISO 4217 三位币种。重量、长度、体积和数量必须带单位。服务端注入 tenant、actor、角色和 scope；客户端输入不得覆盖这些身份字段。

### 7.4 契约与所有权变化

如果需求必须改变公共字段、状态、权限、版本或共享包络，Agent 不得直接修改 `docs/contracts/**`。它只能按仓库规则生成 RFC，说明动机、兼容性、迁移、测试和回滚，等待基线维护者接受后再实施。

## 8. 构建报告

每次构建生成机器可读 `build-report.json` 和对应中文摘要。两者必须清楚标识：

- `generated`
- `locally_verified`
- `fixture_verified`
- `pending_adapter_verification`
- `blocked`
- `release_candidate`
- `released`

`released` 不能由本地构建流程写入，只能由独立发布流程在获得授权并完成读回证据后设置。

构建报告至少包含诊断引用、变更文件、执行命令、实际输出摘要、测试范围、数据模式、外部依赖状态、未验证项、阻断项、当前 Git SHA 和是否具有发布资格。

## 9. 失败闭合

- 描述不足时保持 `needs_more_information` 并继续逐题询问。
- 已有能力能够满足时返回复用方案，不生成重复模块。
- 正式 API、版本、合同或 readiness 证据缺失时，可以生成接口设计和 fake 测试，但必须标记 `blocked_by_authority` 或“待适配验证”。
- fixture 通过只证明本地结构、契约和映射，不证明真实业务可用。
- 外部权威源不可达时，不得使用网页搜索、旧快照、截图、聊天或模型猜测作为替代。
- `ready=false`、`test_data=true`、版本冲突或来源缺失不得提升为 `success`。
- T2 写入必须验证服务端身份、幂等、审批、失败恢复和写后读回。
- T3 动作在第一版不得被自动执行。

## 10. 验证策略

### 10.1 需求验证

- 诊断卡已经由用户明确确认；
- 验收标准可观察、可判定；
- 假设、缺失信息和非目标清楚列出。

### 10.2 契约验证

- Schema 为 Draft 2020-12 且默认封闭；
- 统一包络和五种状态合法；
- 金额和单位符合仓库规则；
- tenant/actor 只由服务端注入；
- 计算结果具有规则/数据版本、source refs、assumptions、warnings、blockers 和 trace。

### 10.3 实现验证

- 先运行预期失败的精确测试，再实现最小变更；
- 运行相关全量测试、类型检查、lint 和 Schema 校验；
- 运行 `git diff --check`；
- 扫描日志和 fixture，确保没有凭证、客户地址、报价明细、税务材料全文或原始聊天。

### 10.4 运行验证

- 本地服务实际启动；
- 工具目录和模块目录可读回；
- 正例及 `needs_input`、`manual_review`、`blocked`、`unavailable` 负例可复现；
- 模块关闭按逆序释放注册，单模块失败不拖垮其他工具；
- 没有 staging 或真实权威源时只报告本地/fixture 验证。

## 11. 独立发布门禁

本地验证完成后只得到“已验证的发布候选”。Agent 必须重新取得发布授权，并核对：

- 当前 worktree、branch、HEAD、未提交改动和构建制品；
- 来源 SHA、版本、digest、兼容性和回滚方案；
- tenant、actor、RBAC、secret reference 和网络 allowlist；
- 上游 readiness、非测试数据、版本、有效期和来源证据；
- T2/T3 的审批人、幂等、写后读回和审计证据；
- staging 验收结果；
- 全部未验证项和阻断项。

任何关键证据缺失，状态保持“发布阻断”。本地启动、测试通过、fixture、Compose 校验或候选镜像构建都不能单独证明生产发布成功。

## 13. 验收标准

第一版完成时，应能通过至少四个端到端场景证明行为：

1. 用户想“做一个 CBM 插件”，Agent 发现并推荐复用 `cargo.calculate`，不生成重复模块。
2. 用户想在 Codex 中使用现有 MCP，Agent 走客户端接入路径，生成无凭证示例并要求 staging 读回。
3. 用户提出一个具备正式只读 API 的新物流查询能力，Agent 形成 T1 诊断卡，经确认后生成最小模块、契约、fake HTTP 测试和构建报告。
4. 用户要求根据聊天记录自动定价并发送报价，Agent 识别权威源和 T3 风险，拒绝生成可执行生产动作，输出阻断项和所需正式合同。

所有场景都必须证明：未经用户确认不修改实现；fixture 不升级为生产可用；本地构建不升级为已发布；公共契约变化只能通过 RFC。

## 14. 后续实施顺序

书面规格经用户复核后，再创建详细实现计划。实现顺序应先建立 workflow 与 Schema 的失败测试，然后补机器入口和中文手册，再增加受控模板与端到端场景。第一版不实现通用 CLI、远程安装器或生产热插拔。
