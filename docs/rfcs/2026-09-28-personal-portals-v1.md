# RFC：个人账号与独立业务门户

- 日期：2026-09-28
- 产品决定：用户明确要求权限全部归个人，取消企业授权；客户与运营分端，运营可编辑现有模块，并授权按更新手册开始实施。
- 状态：产品范围已确认；各批接口和迁移须有对应实现、测试与读回，不代表已发布。
- 操作与验收：[更新手册](../runbooks/2026-09-28-personal-portals-update.md)。

## 轻量版首版范围

按用户最新要求收敛入口：客户仅“我的业务＋发起询价”，运营仅“业务单、业务设置”，人员和邮件放账号设置。每票一个负责人，询价到完成复用同一详情页；不增加独立工作台、逐节点岗位编排或自动审批规则系统。后台细分状态、已有审核及数据隔离继续保留。

GUI 按当前任务组织：同一票分“需求与报价、进度与记录、资料”三个页签，每个任务突出一个明确主操作；费用就地编辑，保存与对外发布分开，错误保留输入。沿用现有组件，补齐键盘、焦点、窄屏及反馈状态，不新增 UI 框架或多步向导。实际交互和截图须在实现后验收，详细规则见更新手册。

高频设置为海运费与费用模板，其他已有模块复用现有编辑器。邮件使用六类客户正文和一类内部待办正文，固定事件映射，不引入任意通知规则编排。拟定 JSON 需适配后分项验收，不直接部署其全部默认模板。

邮件覆盖询价、报价、委托提交待接单、运营接单、适用运输节点、清关、提柜、直送/拆柜分送、签收、返空及结案。业务记录与通知任务一起持久化，异步发送状态关联原事件；不同受众分开发送，机器事件不构成供应商作业批准或客户同意。正文类别复用但节点语义明确，清关放行、场站可提、提柜实际完成等不可互相推断。客户提交委托也收到“待接单”回执，取代此前仅页面回执的规划。

结合工作簿的操作细化：两种服务均支持整柜直送或拆柜分送。城市/目的仓方案复用费用模板，组合收费保留原金额及包含范围，与同范围单项收费核对去重；基础海运费仍只有一个维护来源。同行售价不作为采购成本，未知成本不填零。分送记录在原票内保留目的地及签收，返空可在拆柜后独立完成，不新增仓库库存或产品规则系统。上述细化为本轮规划，不宣称数据已迁移或运行时已支持。

订单跟进复用现有 Case 事件、报价版本、执行及通知记录，在票内显示一条流转时间线。首版补充本票下一步和可选跟进时间，列表筛选今天/逾期待办；不另建流水权威表或任务系统。客户与内部记录在服务端按个人及对象范围过滤，正式业务动作与普通沟通备注分开。具体字段及接口须在实现时补充相应 Schema、迁移和权限测试。

## 原因及边界

2026-09-28 用户确认追加业务闭环：分阶段承接条件、资料提交后运营核对、执行方接受确认、按柜关键期限、追加费用确认、分币种账款跟踪、异常/取消/售后和中途接入。全部复用原票与已有服务，不引入供应商门户、自动读邮箱、支付接口或会计总账。需求字段、行为和 AC-01 至 AC-10 见更新手册；涉及写接口的批次须补充对应版本化 Schema、失败语义及隔离测试后才可运行。当前界面整理不改变业务 API 或计算合同。

当前一个导航混合客户询价与平台审核，原生模块又依赖企业成员关系。分离门户须同时解决服务端的个人授权，不能用隐藏菜单代替权限。

本次维护 apps/console、Portal 人员服务和相应测试；复用现有身份服务、Case、配置仓储与文档服务。不会改变 MCP 静态工具注册、五种响应状态或领域计算公式。

## 权限与兼容

人员 ID 来自已验证会话。客户默认只有本人业务权；运营访问和模块编辑/发布需服务端个人授权。权限响应是界面提示，实际动作仍重新校验。旧企业归属不是个人授权证据，不自动转成管理员。

现有 enterprise API/Key 合同在迁移完成前仅作为兼容路径保留，不进入新门户的日常导航，不静默改变旧 Key 的 scope。新的人员操作与 CLI 使用同一服务端权限。机器权限切换须单独验证。

示意旧授权依据：`{organization_id, membership_role}`。
目标依据：`{actor_user_id, module, action, owner_user_id}`，actor 与 owner 由服务器确定，客户端不能注入 actor 或存储范围。

## 迁移与回退

不删除旧组织资料、配置、报价或凭证。先输出明确的归属清单，在隔离副本核对后迁移。无法确认的记录保持待核对，不分配给当前管理员。新配置使用独立个人存储范围，历史版本保持不变。

门户切换是可回退的路由和页面变更；配置回退使用已有版本操作。发生个人写入后不得直接切回不理解新权限的旧写进程。生产迁移必须备份、停止旧写入者并核对数据完整性。

## 验证

覆盖无企业个人编辑/发布、编辑与发布分权、跨账号拒绝、撤权、服务端身份不可覆盖、CSRF、幂等、版本冲突、重启持久化、客户与运营导航隔离及登录回跳。使用本地合成数据。执行 agent standards、agent pack、相关测试、类型与 Schema 校验和 diff 检查。实际结果记入更新手册。

## 本批接口与兼容（2026-09-28）

复用 `fcl-execution@2026-09-23.v1`，客户动作加入现有 FCL HTTP/CLI 动作表，生成闭合请求/响应 Schema：

| 动作 | 约束 |
| --- | --- |
| customer-claim | 已验证个人邮箱与原询价一致，且持有有效查询凭证；仅凭邮箱或编号不能认领 |
| customer-list / get / pdf | 只读本人认领记录；报价仅对客金额、条款和服务范围，PDF 验证原摘要 |
| customer-quote-publish | 原受理人发布已审核且已导出 PDF 的指定版本；未认领先提示客户关联 |
| customer-confirm | 客户确认指定 offer_id；过期、换版、需求变化拒绝；重复确认不重复通知 |
| customer-order-get / accept | 原受理人读取确认并接单；同票唯一执行，复用正式报价、交接和执行门禁 |

旧：内部 handoff 仅记录移交；新：offer → 客户确认事件 → 运营接单 → 原执行记录。客户确认用现有 `signed_document` 证据类型，引用 `portal:<事件ID>`；服务端核对该事件、客户归属与发布版本，不信任调用方声明。

数据复用 `business_case_events` 的 `portal_*` 事件，原 owner、企业关联、历史报价和凭证不修改；没有客户归属证据的历史票保持未关联。邮件扩展使用 `extensions.customer_notice_v1`，复用执行 outbox、claim/lease、结果核实与重试。新增客户事件与通知同事务；接单邮件随执行创建同事务。未核验询价只发送不含业务资料的回执。

运营身份取现有服务端个人 `operator` 角色或固定受理人配置，不能由页面选择；执行参与人仍按原节点授权。客户入口 `/customer/`，运营入口 `/ops/`，复用页面组件和登录；旧 `/console/` 保留兼容入口，旧 FCL 写 API 同样执行个人运营校验。

示例：`customer-confirm` 输入为 `{"case_ref":"UUID","offer_id":"UUID","confirmed":true}`，操作者由会话注入。客户回应状态使用业务字段 `state=awaiting_acceptance`，不扩展统一包络状态。实际 Schema 位于 `schemas/access-gateway/fcl/customer-*.schema.json`。

回归：个人权限拒绝、证明认领、换版/过期拒绝、重复提交、出队失败、事务回滚、PDF 隔离、Web/CLI 同记录及手机页面。回滚需同时保留 Case/Document/Native 数据备份；产生客户确认后不能删除新事件或降级写入程序。生产迁移沿用执行 v2 离线门禁；本批不操作生产。
