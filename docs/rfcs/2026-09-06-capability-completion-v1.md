# RFC：平台缺口补齐 v1

状态：accepted for implementation and isolated verification。接受依据：2026-09-06 用户明确要求“把缺少的功能做完，企业微信不需要”。根代理承担本轮基线、平台、接入、门户与集成责任；本授权不包含发布税则、批准价格、代领供应商凭证或执行生产业务写入。

## 范围与权威

1. 修复 PR #12 的四项问题：生产 T0 REST 回到 MCP Runtime 的受控派发和持久审计；鉴权就绪包含在线应用权威；上游流式响应实行实际字节上限；成功认证持久记录 Key 最近使用时间。
2. 增加有界、脱敏、租户隔离的业务调用记录与用量视图。审计只记录身份引用、工具、请求号、结果状态、耗时和时间，不保存请求/响应原文。
3. 为五项现有只读业务能力提供 MCP 接入，并保持旧 `t0-v1` 的精确三工具合同。新增显式业务 profile 和版本化换票合同；原工具输入输出、Business 授权与来源就绪规则不改变。
4. 补齐关务/税费历史入口与来源记录读回适配。平台只保存来源签发的 opaque 记录引用；禁止复制关税结果、报价、客户或文档主表。来源缺少记录合同或未发布时返回 unavailable，不假造可恢复历史。
5. 按 Module Contract v1 增加签名制品验证、受控激活、generation 固定、排空、回滚与目录通知；保留原静态 profile 兼容。T1 模块通过隔离的私有 Provider 执行，不能在 Gateway 任意加载代码。
6. 增加可用于多实例部署的共享 Portal/会话/授权持久化与并发控制、迁移及恢复验证。SQLite 模式保留为明确的单实例兼容模式。
7. 企业微信登录不再属于产品缺口或本轮验收项。发送、订舱、付款、正式报关和商业计费继续不在范围内。

## 兼容性与最小合同

既有五状态、闭合 Schema、服务器身份、短期 JWT、幂等、权限变更立即生效、来源版本与写后读回规则保持有效。旧 Key 和已撤销状态不重建、不复活，不因新 profile 自动增权。

旧换票示例保持不变：

```json
{"schema_version":"application-exchange@2026-09-06.v1","requested_tool_names":["cargo.calculate"]}
```

业务 MCP 的新增换票使用单独版本，允许已批准的既有业务操作；实际声明以独立 Schema 为准，不扩张旧 T0 allowlist。调用记录接口使用只读分页与时间范围，服务端从人员会话解析组织和应用访问范围；跨租户查询返回拒绝，不能接受任意 tenant 参数。

历史读回只有在来源签发引用、对象权限和结果合同验证后才能成功；不提供浏览器本地缓存冒充来源记录的回退。

## 所有权与迁移

本轮基线维护：本 RFC、相关新增合同/Schema、产品说明和实施记录。平台维护：`src/logistics_mcp/{server,platform,module-runtime,control-plane}/**`。接入与持久化维护：`services/access-gateway/**`、`schemas/access-gateway/**`。门户与集成维护：`apps/console/**`、`deploy/**`、`.github/workflows/**` 及对应测试。先完成合同与失败用例，再实现；不修改其他业务权威仓库。

新增持久结构使用显式版本迁移，不拷贝 fixture 人员/Key 到生产。已有数据库可读升级，回滚保留新增审计和记录引用；旧服务不能绕过新的凭证撤销状态。

## 验证与回滚

每个切片先运行会失败的行为测试，再实现和运行相关回归。最终运行 build、全量 Vitest、typecheck、lint、Schema/Agent 标准与适配器验证、fixture 发布检查、门户浏览器流程及 CI 镜像构建。多实例验证必须包含并发更新、重启、会话/撤销跨实例可见性和故障恢复；热切换验证必须包含旧代在途、新代拒绝/回滚和清理。

发布前仍需真实来源合同、配置与业务资料。回滚通过旧镜像/profile 路由切换，保留持久记录；不得恢复失效 Key、丢弃未知写结果或把历史生产回执当作本轮部署证明。
